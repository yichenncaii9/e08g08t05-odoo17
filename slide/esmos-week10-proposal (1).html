Deployment Approach

Azure Kubernetes Service.

Option 4 — self-scaling Kubernetes in Southeast Asia. Three layers: Nginx Ingress for routing, application pods for Odoo and Moodle, and PostgreSQL on persistent storage.

Why AKS Over Simpler Options

Five justifications.

  • Horizontal Pod Autoscaler— meets 50-concurrent-user training days without over-provisioning
  • Rolling updates— zero-downtime deployments, critical for healthcare uptime
  • Self-healing— auto-restarts failed pods, recovery in seconds not minutes
  • Compliance— single cluster in Southeast Asia. K8s RBAC enforces least-privilege
  • Cost— free control plane. B2s node ~$30/month within student credits

Validation Plan

Every claim gets tested before go-live.

  • Training platform capacity— 50 concurrent Moodle users complete a course without degradation. Measured via k6 or Locust against Moodle endpoint. Pass: page load remains under SLA threshold.
  • Helpdesk throughput— Odoo handles concurrent ticket submissions from guest portal users during peak onboarding window. Leverages existing load test baseline from PM1 staging tests.
  • WAF latency impact— before/after response time comparison with ModSecurity enabled. Confirms security layer does not degrade user experience beyond acceptable margin.
  • Self-healing recovery— pod failure simulation (kubectl delete pod) with measured time to automatic replacement. Validates AKS self-healing claim and confirms MTTR under SLA target.

All tests to be executed and evidenced during Week 12 live demo. This slide presents our testing strategy, not results.

RFC 1 — Non-Functional Change

Nginx reverse proxy with WAF.

  • Static asset caching— Nginx serves CSS, JS, images from memory
  • Response compression— gzip reduces bandwidth ~60–70%
  • Rate limiting + WAF— OWASP CRS blocks SQLi, XSS, brute-force

Success criteria: before/after load test and attack simulation to be demonstrated during Week 12 live demo.

The ITIL Lifecycle Loop

Why this change —
evidence, not theory.

  1. PM2 Incident — web defacement attack compromised production Odoo
  2. Problem Management — RCA found zero application-layer defenses
  3. Change Management — RFC to implement WAF as preventive measure
  4. Continual Improvement — monitor blocked threats, validate effectiveness

RFC 2 — Process Change

MFA enforcement on all Odoo accounts.

  • What changes— TOTP authenticator required before any operational Odoo account activates
  • Why separate from RFC 1— process-level change with user friction; different risk profile from the infrastructure-only WAF change
  • Approval path— normal change requiring CAB sign-off; estimated 2 weeks including change management
  • Workflow impact— adds one step to onboarding BPMN after Odoo account creation

Risk: Medium. User friction may delay onboarding if staff encounter TOTP setup issues. Mitigation: helpdesk support during rollout window.

Source: Week 6 homework identified MFA as the permanent fix for the account privilege abuse that enabled the PM2 web defacement incident.

Operations & Support

Onboarding workflow.

  1. Staff submits Odoo Access Request via helpdesk guest portal
  2. Support Manager logs service request ticket
  3. Staff completes Moodle compliance training
  4. Staff submits completion proof via ticket update
  5. Support Manager verifies Moodle records — if incomplete, returns with specific modules required
  6. System Configurator creates Odoo account with least-privilege role and confirms on ticket
  7. Staff receives credentials and completes mandatory password rotation on first login

Across Both Systems

Incident and change handling.

Any disruption to Odoo or Moodle triggers a helpdesk ticket with RASCI-defined escalation. Support Manager triages, System Configurator resolves, Security Manager consulted for security events.

All non-emergency changes go through the RFC process — documented in helpdesk, reviewed by Change Authority, with rollback plan before execution.

What we monitor

We detect problems
before staff experience them.

  • Service availability— synthetic health checks hitting Odoo and Moodle endpoints every 30 s. Alert fires within 1 min if either is unresponsive. (Better Stack)
  • Infrastructure health— CPU, memory, disk, pod status via Azure Monitor. Warning alerts at 70% utilisation to catch issues before they become outages.
  • Security events— WAF blocked-request counts confirm application-layer protection is active. Spikes trigger investigation.

Why this matters

  • LTA lesson applied — their buses ran on schedule but arrival data was wrong. Infrastructure uptime alone misses service quality failures. We monitor what staff actually experience: can they log in, load pages, submit tickets?
  • PM2 lesson applied — the web defacement went undetected because we had no content monitoring. Post-WAF, we monitor both blocked threats and whether service content is intact.
  • Audit-ready — monitoring dashboards provide evidence for SLA reporting and incident post-mortems. Every alert is logged.

Monitoring closes the visibility gap from PM2 — we now detect threats blocked and service degradation, not just outages.

  • Cost guardrails— Azure alerts at 60% and 80% thresholds; ~3 months runway on $100 credits

Key Risks

Mitigated, not ignored.

  • AKS learning curve— team has Azure DevOps and Docker experience; Kubernetes is an incremental step
  • Credit burndown— Azure Cost alerts at 60% and 80%; deallocate nodes outside business hours
  • WAF false positives— back-out removes ModSecurity without touching Odoo or Moodle
  • Scope management— all RFC work tracked via helpdesk tickets with rollback plan required before execution

Security Posture

Defense in depth.

  • Data residency— all workloads in Azure Southeast Asia, satisfying regulatory compliance requirements
  • Access control— no Odoo access without verified Moodle training completion, enforced through the onboarding workflow
  • Layered defense— Azure RBAC + K8s namespaces + Odoo roles; a breach in one layer does not compromise the others
  • WAF (pending RFC 1)— blocks common web attacks before they reach applications; closes the gap identified in the PM2 incident
  • MFA (pending RFC 2)— authenticator app required for all operational accounts; prevents unauthorized access even if credentials are compromised
  • Audit trail— every ticket, request, and incident tracked to closure via the compliant helpdesk
