Business Context

The healthcare client approved ESMOS for production.
They cannot go live yet.

Three capabilities must be in place before launch: compliant meal operations, mandatory staff training, and centralized support — all hosted in Asia Pacific.

Hard dependency: No Odoo access without verified Moodle completion — enforced through the onboarding workflow, not just policy.

  • Odoo Meal plan operations & inventory. 500+ staff, internal-only access.
  • Moodle Mandatory compliance training LMS. 50 concurrent baseline, 100 designed capacity.
  • Helpdesk Unified ticketing for incidents, service requests, and changes. Self-hosted in Asia Pacific.

ITIL 4 Service Value Chain — Plan Activity

Value is created now, in Plan, by making decisions that prevent costly rework later.

  1. Deployment architecture — AKS, Southeast Asia, compliance-first selection
  2. Quality expectations — Kano model: dissatisfiers, satisfiers, and delighters defined before build
  3. SLAs and CTQs — measurable targets negotiated and documented before any infrastructure work begins
  4. Change strategy — two RFCs identified from PM2 lessons learned, to be executed in Design & Transition

What follows Plan: Obtain/Build (AKS deploy) → Design & Transition (RFC execution) → Deliver & Support (helpdesk ops). Each phase feeds back into continual improvement.

Deployment Approach

Azure Kubernetes Service — Southeast Asia.

Single cluster with Nginx Ingress, Odoo and Moodle pods, PostgreSQL on persistent storage. Internal-only access enforced via IP restriction.

  • Self-healing — pod auto-restart drops MTTR to seconds because healthcare uptime requires 24/7 recovery our 5-person team cannot staff manually
  • Auto-scaling (HPA) — Moodle pods scale during training windows because 100 concurrent users must be met without permanent over-provisioning
  • Compliance — K8s RBAC + namespace isolation enforces least-privilege, Southeast Asia region satisfies data residency requirements

~$30/month with free control plane — within Azure for Students budget.

Change Strategy — Proposed

Two RFCs identified from PM2 lessons learned.

This is a proposal. Both changes require formal RFC approval through Change Authority before execution.

  1. RFC 1: WAF + Nginx Reverse Proxy — Non-functional change, no workflow impact.
    Triggered by PM2 web defacement. RCA: zero application-layer defenses. Proposed control: ModSecurity OWASP CRS (SQLi, XSS, brute-force). Demo: before/after load test + attack simulation. Rollback via kubectl rollout undo.
  2. RFC 2: MFA Enforcement — Process-level change, modifies onboarding workflow.
    Adds TOTP setup step before Odoo account activates. Normal change requiring CAB approval due to user friction. Medium risk. Estimated 2-week duration including change management.

ITIL CI loop: PM2 incident → Problem Management (RCA) → Change Enablement (RFC) → Continual Improvement (monitor effectiveness)

Operations & Support

Onboarding, incidents, and changes — all tracked.

  1. Staff submits request via helpdesk guest portal
  2. Support Manager assigns Moodle course — SLA: access within 4 hrs
  3. Completion verified → System Configurator creates Odoo account — SLA: within 24 hrs of training
  4. Ticket closed — full audit trail preserved

Incidents: Support Manager triages (R) · System Configurator resolves (R) · Security Manager consulted for security events (C). All non-emergency changes go through RFC with rollback plan.

Security Posture

Defense in depth.

  • Data residency— all workloads in Azure Southeast Asia
  • Least privilege— K8s RBAC + Odoo role separation (PM2 lesson applied)
  • WAF (RFC 1)— OWASP CRS blocks SQLi, XSS, brute-force (pending approval)
  • MFA (RFC 2)— TOTP enforcement on all Odoo operational accounts (pending approval)
  • Audit trail— all helpdesk tickets tracked to closure
